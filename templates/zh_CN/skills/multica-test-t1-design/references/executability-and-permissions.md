# 可执行性与权限规范（全系统强制）

> 整合自 `test-case-generator-squad`「可执行性与业务贴合性规范」。与 [`generation-workflow.md`](generation-workflow.md)、[`test-case-template.md`](test-case-template.md) 配合。  
> 经验来源：PROJ-123 与 历史用例集对照 — **既像真业务可执行，又可追溯验收标准**。

## 1. 双目标合流（不可偏废）

| 目标 | 要求 |
| --- | --- |
| **可执行（业务向）** | 真实入口、菜单路径、等待加载、命名造数；拿到用例就能在环境里点 |
| **可追溯（验收向）** | 关键规则（数值边界、AND/OR、空态）映射 JIRA AC / PRD；缺陷可定位到验收行 |

**禁止二选一**：只写抽象规则清单、或不追溯 AC 的「漂亮操作步骤」，均不合格。

---

## 2. 登录 / 账号表述（强制）

- **禁止**写死具体登录账号/密码（域账号名、个人测试手机号等）
- **禁止**成稿中留字面 `XXX` / `某某权限` 占位 — Agent 须填入**当前系统真实权限名**

### 权限识别顺序

1. 当前需求文档中的权限/角色说明
2. 关联 Confluence / 设计稿
3. 团队知识库中该系统模块权限口径（Step 0.5b 三问之三）
4. 由菜单/功能推断的最小必要权限（须可验证）

### 书写模板

`登录具备 {系统/产品}【{模块或操作}】权限的账号`

**示例（勿照搬到无关系统）：**

| 场景 | 写法 |
| --- | --- |
| 模块B订单查询 | `登录具备 模块B【订单查询】权限的账号` |
| 模块B概览看板 | `登录具备 模块B【概览看板】查看权限的账号` |
| CRM/MES/系统A | 按该系统实际权限命名，如「具备 CRM 订单详情只读权限的账号」 |
| 分角色 | `登录具备「标签重算」权限的管理员账号` |

**例外**：需求本身验收账号策略/白名单时，可引用需求中的账号规则，**仍禁止写密码**。

**自检失败**：前置条件仍出现 `XXX` / `某某权限` → 生成失败，须补全后再落库。

---

## 3. 步骤必须可落地

- 写清入口路径（如 `系统A → 模块B → 订单查询`）；路径来自需求、关联文档或 KB，**禁止臆造菜单**
- 需加载处写明「等待加载完成」
- 造数用稳定别名（如 `A_ant_ok`），前置给出字段取值
- 文案有别名（「反合」/「反颌」）时步骤注明「以页面实际文案为准」，验证点不模糊

---

## 4. 模块命名贴合产品信息架构

- `module` 路径反映真实业务导航（搜索、详情、看板、后台任务等）
- 不要把「订单查询验证」挂到无关的「某月底数据部分/看板细分」下
- 遵守 `/` 分层与 Issue Key 系统前缀根节点（见 `generation-workflow.md` 模块层级）

---

## 5. 知识库 / 历史：操作进步骤，规则不进验收

- **操作桶必须写入步骤**（路径/权限/文案别名），见 Step 0.5 用法二分
- **规则桶仅供参考** — 不得把历史/知识库规则写成当前验收点
- **自检**：KB 已给出「模块B→订单查询/概览看板」等入口，步骤仍写「打开搜索页/查看看板」泛化描述 → 未落实 KB，须返工

---

## 6. 生成后质量自检（必过）

- [ ] 无写死个人账号/密码；无 `XXX` 权限占位
- [ ] 权限文案已按**当前系统**识别填写（非空套话）
- [ ] 步骤含真实入口或明确后台触发方式
- [ ] 前置含权限 + 造数别名与关键字段值
- [ ] 核心 AC（含严格边界）可追溯；未覆盖写清 uncovered
- [ ] 模块路径与产品导航一致
- [ ] 预期无 `[待补充]` / `待产品确认` 等占位；未决项进 blockers，不进 expected_results
- [ ] 优先级 P1/P2/P3 正确；无 P0

Review 阶段对照 `multica-review-test` 的 `checklist.md` §5–§6。
